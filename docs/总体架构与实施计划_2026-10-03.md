## 2. AI 对这份思路的评价

### 2.1 第 15 行是整份思路里最有价值的一句

```text
"只要不进行固件升级，应该此方法能够通吃"
```

```text
这句话的战略含义：
  不去逆向协议，而是【复用官方 APP 已经建好的连接】。
  → 不需要知道 8 字节命令每一位是什么
  → 不需要标定校验和
  → 不需要知道 ANC 的操作码
  → 官方 APP 支持什么功能，我们就能控制什么功能
```

```text
对比我们现在卡住的地方：
  我们卡在"命令原文拿不到、校验和反推不出来"。
  官方 APP 有完整的协议实现，它自己知道怎么发。
  如果它发的包由我们代发，那我们就不需要懂协议。
→ 思路方向完全正确，而且能绕开当前全部死结。
```

### 2.2 "两头 Hook，模块当媒介"架构成立

```text
┌──────────────────────────────────────────────────────┐
│                     模块（媒介）                      │
│                                                      │
│   系统侧 Hook                     官方 APP 侧 Hook     │
│   ────────────                    ────────────────   │
│   ColorOS 三方耳机接口             com.ugreen.iot     │
│   （参考 HuaweiPods）              RFCOMM SCN=13      │
│        ↑                                ↑            │
│        │ 通知电量/降噪状态               │ 收命令/上报  │
│        │ 接收"切降噪"指令                │             │
└────────┼────────────────────────────────┼────────────┘
         │                                │
    ColorOS 系统                    UGREEN HiTune T6
    （流体云/我的设备/设置页）        （真实耳机）
```

```text
数据流 1（状态上行）：
    耳机 → 官方 APP → [Hook] → 模块 → [Hook] → 系统 → 显示电量/降噪状态

数据流 2（控制下行）：
    系统 UI 点"通透" → [Hook] → 模块 → [Hook] → 官方 APP → 耳机
```

### 2.3 但有两个关键的技术前提，必须先验证

```text
⚠ 前提 A：官方 APP 必须活着
   Hook 只能作用于正在运行的进程。
   如果官方 APP 被系统杀掉 / 用户滑掉，
   我们就没有"执行者"来代发命令了。
   → 需要处理保活，或者接受"官方 APP 必须在后台"这个约束。

⚠ 前提 B：两路通道必须能并存
   已证实的事实：
     · 官方 APP 走 SPP（RFCOMM SCN 13）
     · 我们的测试 APP 走 BLE GATT（77777777）
     · 耳机把同一份协议【同时镜像到两条通道】
     · 但我们两个 APP 连的是同一副耳机，
       之前实测"一边断开另一边也同步断开"
   → 所以【我们的 BLE 订阅 + 官方 APP 的 SPP】
     能不能长期稳定并存，必须专门测一次。
   → 这个测试成本极低（不需要写任何代码），见第 5 节。
```

## 3. 我的补充建议：把战略拆成两段

你的思路是"一劳永逸"，我完全同意终局目标。但实施上建议分两段走，
因为**第一段能立刻验证可行性，且不需要研究 ColorOS 系统接口**：

```text
第一段（协议桥）：只做"官方 APP 侧 Hook"，先不碰系统
   目标：证明"我们能借用官方 APP 的手去控制耳机"
   产出：命令原文 + 校验和算法 + ANC 操作码 + 双向日志
   价值：把"协议完全确定"这件事一次性做完，
         同时验证前提 A / B

第二段（系统桥）：接入 ColorOS 三方耳机能力
   目标：让系统认识 T6，显示电量、接管降噪入口
   参考：HuaweiPods-ColorOS-1.8.3-coloros.1.apk（已在 交流\）
   依赖：第一段已经确认状态字节的含义（如游戏模式的 01/00）
```

```text
这样分的好处：
  第一段失败 → 说明 Hook 路线不可行，及时止损，不用白研究系统接口
  第一段成功 → 第二段只需要做"翻译"，不用再做逆向
```

## 4. 终局架构（两段都完成后的形态）

```text
【路线甲】纯借用（你的原思路）
   模块 Hook 官方 APP，所有命令都交给官方 APP 代发。
   ✅ 通吃所有功能，永远不用逆向
   ❌ 官方 APP 必须常驻运行
   ❌ 官方 APP 一升级，Hook 点可能要跟着改

【路线乙】协议自持（第一段的副产品）
   第一段已经拿到完整协议 → 模块/APP 自己实现 RFCOMM，
   完全不需要官方 APP。
   ✅ 不依赖官方 APP，不依赖 Hook
   ❌ 需要自己实现 SPP 连接（SCN 13 已确认）
   ❌ 新功能（比如新固件特性）要重新逆向

【推荐】先甲后乙
   用甲快速拿到全部协议 → 再决定要不要升级成乙。
   而且甲的成果（协议表）是乙的输入，
   两条路线不冲突，甲永远不浪费。
```

## 5. 【立刻可做】两个零成本验证实验

在写任何 Hook 代码之前，先确认两个前提，避免白干活。

```text
实验 A：两路通道能否并存（验证前提 B）
   步骤：
     1. 我们的测试 APP：连接 T6 → 订阅 Notify → 清空日志
     2. 打开官方"声学"APP，确认它连上 T6
     3. 静置 60 秒不要操作
     4. 切回我们的 APP，复制日志
   判读：
     ✅ 我们仍能收到 9.4 秒周期包 → 两路可并存，架构可行
     ❌ 我们的日志断了 / 连接被踢 → 需要换方案（比如我们只发命令不订阅）

实验 B：官方 APP 被杀掉后，耳机连接会怎样（验证前提 A）
   步骤：
     1. 官方 APP 连上 T6
     2. 在最近任务里把官方 APP 划掉
     3. 看耳机的连接状态（系统设置里的蓝牙页）
   判读：
     连接保持 → 说明连接由系统/耳机维持，APP 只是客户端，保活压力小
     连接断开 → 说明官方 APP 是连接持有者，必须保活
```

```text
这两个实验都不需要改代码、不需要装模块，
只需要你操作 + 复制一份日志给我。
建议先做这两个，再决定 Hook 模块怎么写。
```

## 6. Hook 模块技术方案（第一段实施细节）

### 6.1 Hook 点

```kotlin
// 主方案：标准 SPP socket
android.bluetooth.BluetoothSocket.getOutputStream()
    → 保存返回的 OutputStream

java.io.OutputStream.write(byte[])          // TX ★核心
java.io.OutputStream.write(byte[], int, int)
java.io.OutputStream.write(int)

android.bluetooth.BluetoothSocket.getInputStream()
java.io.InputStream.read(byte[], int, int)  // RX，用于交叉验证
```

```text
为什么选流层：
  与 APP 内部实现完全解耦，不依赖混淆后的类名。
  只要它用标准 SPP socket，就一定能抓到。
```

### 6.2 备用 Hook 点（主方案抓不到时）

```text
绿联 APK 里的私有线索（来自第一任静态分析）：
    UGREENEarConnectionController
    UGREENBleConnect
    UGREENDeviceConroller
    writeChar / writeCharacteristic / sendSppData / writeDataToSppDevice
    IBluetoothSpp / BluetoothSpp
→ 直接 hook 这些方法名，抓入参 byte[]
```

### 6.3 过滤策略

```text
只记录同时满足：
  1. 进程包名 == com.ugreen.iot
  2. 远端地址 == 90:A0:BE:2D:5E:CA

原因：手机同时有 4 条蓝牙链路（handle 22/5/10/11），
      不过滤会混入 A2DP / HFP / GATT 数据。
```

### 6.4 落盘与导出

```text
落盘：模块私有目录 /data/data/<module>/files/ugreen_protocol.log
      （不需要存储权限，不碰系统分区）

格式：
    15:00:20.399  TX  8B   85 86 87 04 01 ?? ?? ??
    15:00:20.462  RX  9B   DD EE FF 08 01 01 01 23 15

导出：
    A. 模块自带 Activity + "复制全部"按钮（用户可随时复制）
    B. adb 从模块私有目录只读 pull（AI 自己取，不占用用户时间）
```

## 10. 风险登记

```text
风险 1  Hook 不到（APP 不用标准 BluetoothSocket）
   → 回退：hook 绿联私有类（sendSppData 等）

风险 2  官方 APP 被杀，命令发不出去
   → 对策：保活（前台服务/白名单），或走路线乙

风险 3  两路通道不兼容（实验 A 失败）
   → 对策：模块不自己订阅 BLE，只负责转发；
           状态也全部从官方 APP 的 RX 里取

风险 4  官方 APP 升级导致 Hook 失效
   → 对策：Hook 在流层（稳定），尽量不 hook 私有方法

风险 5  误触固件升级（用户提醒过）
   → 对策：Hook 只读日志、不拦截；不在官方 APP 里点固件升级入口；
           后续若要发命令，白名单限定为状态类/降噪类操作码
```
