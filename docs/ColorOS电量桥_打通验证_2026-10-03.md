## 3. ★ 跨进程文件共享的路径选择（踩了 4 次坑，务必记住）

```text
路径                                   SELinux 标签                   蓝牙域可读
/sdcard/Download/...                   media_rw_data_file             ✗ FUSE 拒绝
/sdcard/Android/data/<pkg>/files/...   media_rw_data_file             ✗ FUSE 拒绝
/data/local/tmp/ugreen_bridge/...       shell_data_file                ✗ 跨域被拒
/data/misc/bluetooth/logs/...          bluetooth_logs_data_file       ✅ 唯一可行
```

```text
[教训 - 非常重要]
   跨进程共享文件时，【光看权限位不够，必须看 SELinux 标签】。

   我一开始看到文件是 -rw-rw-rw- (666) 就以为没问题，
   实际被 SELinux 的 MAC 策略挡住，绕了好几轮才想到查 ls -Z。

   排查命令：
       ls -lZ <path>          # 看 SELinux 标签
       getenforce             # 看是否 Enforcing
       dmesg | grep avc       # 看拒绝记录
```

```text
[另一个坑] 蓝牙进程（uid 1002）写不了 /sdcard 与 /data/local/tmp，
           只能写 /data/misc/bluetooth/logs（它自己的目录，0770 bluetooth:bluetooth）。
           而普通 APP 写不进那个目录 → 必须用 su。
```

## 6. 实现中的关键细节（复用价值高）

### 6.1 ClassLoader（★ 极易踩坑）

```text
❌ ColorOsBatteryBridge.class.getClassLoader()
   → 模块自己的 ClassLoader，看不到蓝牙进程的类
   → 真机表现：所有类报 "类不存在"

✅ lpparam.classLoader（LSPosed 在 handleLoadPackage 给的）
   → 从 HookEntry 注入到 ColorOsBatteryBridge
```

```text
[真机对比证据]
第一次探测的 ClassLoader：zip file "/system/app/Bluetooth/Bluetooth.apk"
第二次探测的 ClassLoader：zip file "/system/app/Bluetooth/Bluetooth.apk",
                          zip file "/system_ext/framework/oplus_bluetooth_common_ext.jar"
                          ↑ 多了这个，Oplus 的类才能被找到
```

### 6.2 双重触发（★ 解决类未加载）

```text
问题：handleLoadPackage 在【进程创建最早期】执行，
      那时 AdapterService 等类还没被加载。

方案：
   第 1 次：进程加载时装一遍
   第 2 次：Hook AdapterProperties 的【构造函数】，等蓝牙服务初始化后再装

为什么钩构造函数：它不会随版本改名（方法名可能改），
                  且蓝牙初始化时一定构造。
```

### 6.3 AdapterService 的 4 条获取路径

```text
1. 宿主自身（如果 Hook 的就是 AdapterService）
2. context.getAdapterService()
3. 静态字段 sAdapterService / sInstance / INSTANCE
4. 从 AdapterProperties 实例的 mAdapterService 字段反取   ← 实际生效的是这条
```

### 6.4 失败路径必须留日志

```text
踩坑：最初 readLevels() 读不到就静默 return，
      结果是"日志里什么都没有"，完全无法定位。

修复：每一环都留痕
   · 读不到文件 → 打印候选路径列表（只打一次，避免刷屏）
   · 准备推送   → 打印数值
   · 推送成功   → 打印数值
   · 推送失败   → 打印原因（只打一次）
```

## 7. 下一步的两个方向（待用户确认显示情况后定）

### 方向 A：接管原生通道

```text
目标：让【我们的值】赢过原生上报
做法：Hook 蓝牙栈里原生上报的那个调用点，
      把它的值替换成我们从 BLE 读到的精确值
难点：时序（谁最后写谁赢）
```

```text
目标：像官方 APP 一样分别显示 左耳 / 右耳 / 电池仓
做法：查 IOplusRemoteDevice 的其它方法，
      或看官方 APP 用什么 API 显示三组电量
理由：单电量系统本来就有，分耳显示才是实质差距
```

```text
[推荐 B] 用户明确说过"电量不是重点，先让它能用"，
         且单电量原生已有 → 价值在系统没有的那些。
```
