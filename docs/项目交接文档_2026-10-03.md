# 4. T6 私有协议（核心资产）

## 4.1 命令帧结构

```text
偏移  含义
0-2   固定头 AA BB CC
3     功能域：09=降噪/环境音  08=游戏模式  04=状态查询  01=心跳
4     固定 01
5-6   参数
7     由内容决定的确定性值（算法未知，抄现成值）
```

## 4.2 降噪命令表（全部真机验证）

| 含义 | 参数 | 完整命令 | 应答 |
|---|---|---|---|
| 降噪 关 | A0 | `AA BB CC 09 01 A0 A0 2A` | `DD EE FF 09 01 01 A0 5C C6` |
| 降噪 深度 | A1 | `AA BB CC 09 01 A1 61 EA` | `DD EE FF 09 01 01 A1 7D D6` |
| 降噪 中度 | B1 | `AA BB CC 09 01 B1 60 26` | `DD EE FF 09 01 01 B1 4C C4` |
| 降噪 轻度 | C1 | `AA BB CC 09 01 C1 61 C2` | `DD EE FF 09 01 01 C1 DB BA` |
| 环境音 | C2 | `AA BB CC 09 01 C2 21 C3` | `DD EE FF 09 01 01 C2 B8 8A` |
| 游戏模式 开 | 01 | `AA BB CC 08 01 01 30 52` | `DD EE FF 08 01 01 01 23 15` |
| 游戏模式 关 | 00 | `AA BB CC 08 01 00 F1 92` | `DD EE FF 08 01 01 00 02 05` |
| 状态查询 | 00 | `AA BB CC 04 01 00 31 91` | 27 字节状态包 |
| 心跳 | 00 | `AA BB CC 01 01 00 21 90` | 无 |

## 4.3 校验和：未解开，也不需要解开

```text
第 7 字节由帧内容唯一确定（同一参数跨会话完全相同），但：

  前缀求和（所有长度）                                ✗
  前缀异或（所有长度）                                ✗
  sum ^ xor 组合变体                                  ✗
  CRC-8 全家族（256 多项式 × 初值 × 反射 × xorout）    ✗

反编译也没找到（帧构造在混淆 JS / 原生库里）。

→ 采用【方案甲：抄现成值】。命令是固定常量，原样回放即可。
```

## 4.4 ★ ColorOS 模式值（最容易搞错的地方）

```text
从 SystemUI 的资源表反查确认（qs_noise_reduction_*）：

    5  = 降噪      qs_noise_reduction_open         = "Noise cancellation"
    2  = 通透      qs_noise_reduction_transparent  = "Transparency"
    1  = 关闭      （默认标签）
    10 = 自适应    qs_noise_reduction_adaptive     = "Auto"

循环顺序由 SystemUI 的 iArr = {1,5,10,2} 过滤而来：
    关闭 → 降噪 → 通透 → 关闭
```

```text
[踩坑记录] 最初凭直觉写成 1=降噪 / 5=通透 / 2=关闭，
           结果三档标签全部错位（用户实测：
           选关显示通透、选开显示关闭、选环境音显示降噪）。

[教训] 枚举值必须去资源表/字节码里查实际定义，不能猜。
```

# 5. 两套系统 UI 的接管方法（可复用到其它耳机）

## 5.1 音量面板（com.oplus.melody）

**链路**：SystemUI → `EarphoneControlProvider` → 显示降噪卡片

**关键类**：`com.oplus.melody.provider.EarphoneControlProvider`

**需要伪造的两个查询**：

```java
// ① melody_method_active_device —— 告诉系统"当前活动设备是谁"
MatrixCursor({name, address})
    → [UGREEN HiTune T6, 90:A0:BE:2D:5E:CA]

// ② melody_method_noise_reduction —— 当前模式 + 支持的模式
MatrixCursor({name, address, "type", "supports"})
    → [UGREEN HiTune T6, 90:A0:BE:2D:5E:CA, 5, "[1,5,2]"]
    // supports 是 JSON 数组，SystemUI 用 Gson 解析成 List<Integer>
    // type 是当前模式，SystemUI 直接用它显示标签
```

**接收用户切换**：Hook `call(String, String, Bundle)`，method = `melody_method_noise_reduction`，bundle 里 `address` + `type`。

**★ 关键：让卡片显示出来的两个额外条件**

```java
// SystemUI 的 NoiseReductionDetailTile.isAvailable()
return (supportType["noise"].size() > 1)   // ① supports 至少 2 个有效模式
    && (earState != 0);                     // ② 佩戴状态非 0
```

`earState` 只能靠**主动通知内容变更**来设置：

```java
contentResolver.notifyChange(URI_EARPHONE, null, 1281);
// flags=1281 的位含义（来自 SystemUI 的 ContentObserver）：
//   1281 & 65280 = 1280  → 进入"佩戴状态"分支
//   1281 & 1     = 1     → 判定为已佩戴
```

**★ 让标签即时刷新**：

```java
contentResolver.notifyChange(URI_EARPHONE, null, 512);
// 512 → SystemUI 的 onNoiseReductionTypeChanged()
// 不通知的话，必须退出音量面板再进来才刷新
```

## 5.2 设备空间（com.heytap.mydevices）

**思路来源**：HuaweiPods（已反编译确认）

**Hook 点**：

```java
com.heytap.mydevices.plugin.bluetooth.fragment.BtDetailPageFragment
    .onViewCreated(View, Bundle)
```

**流程**：

```text
① 反射遍历 Fragment 及父类的 String 字段，找符合 MAC 正则的值
   → 识别出是不是目标设备（不写死字段名，抗混淆）

② findPreference("pref_bt_audio_settings")
   → 系统自带的"蓝牙音频设置"条目

③ ★ 不依赖任何 Preference API（COUI 库被混淆，方法名全是 A/B/C）
   改为按【签名 + 字段类型】识别绑定方法：
     · 挂上所有"参数里可能带 ViewHolder"的方法
     · 回调里找"持有 View 类型字段"的对象 → 那就是 itemView

④ 改 itemView 的文字（android.R.id.title / summary，找不到则递归收集 TextView）
   并每次都重挂 OnClickListener（RecyclerView 会复用 View，只挂一次会被覆盖）

⑤ 状态变化时刷新已显示的列表项（否则外面摘要停在旧值）
```

**★ 关键坑：RecyclerView 复用**

```text
绑定 1：系统设监听 → 我们设我们的        → 我们赢
绑定 2（同一 View 复用）：系统重设监听
                        → 若我们去重跳过   → 系统赢（点击跳去蓝牙设置页）

所以监听必须【每次绑定都重设】。
```

## 5.3 设备快连（com.heytap.accessory）—— 为何放弃

```text
华为的做法（to.java，已反编译）：
    hook Resources.getDrawable  → 替换弹窗图标
    hook View.performClick      → 劫持点击
    hook DialogActivity.onCreate / dispatchTouchEvent → 识别与追踪

注意：它是【改造已经弹出来的弹窗】，而不是创建弹窗。
```

**我们做不出来的原因**：

```text
① 该弹窗是为"发现【未配对】的新设备，引导配对"设计的
   → T6 早已配对，不走这条路

② 需要系统扫到设备广播
   → 真机日志显示扫描 Filters 里有 T6，但 Results: 0/0/0
   → 因为 T6 连着手机时不广播

③ 即使扫到，还要过 TriggerState / FilterReason / DialogSceneGuard
   → 这三个是系统/云端策略，无法查看也无法修改

④ 华为能用的前提是它的耳机在 ColorOS 的"认识列表"里，我们不是
```

**顺带挖到的信息（对未来有用）**：

```text
com.heytap.accessory.permission.ACCESSORY_FRAMEWORK     插件权限
com.heytap.accessory.plugin.discovery.IDiscoveryRequest  插件接口
com.heytap.accessory.plugin.discovery.IDialogEventCallback
com.heytap.accessory.plugin.discovery.action.DIALOG      触发动作
→ 理论上可走"配件插件"正道，但权限很可能是 signature 级
```

# 7. 全部踩过的坑（★ 最重要的一节）

## 7.1 跨进程 SELinux（花了最久）

```text
现象：系统桥读不到测试 APP 写的电量文件，日志"什么都没有"

排查路径：
    文件存在、权限 666 → 不是权限位问题
    → 查 SELinux 标签 → 找到根因

路径                                    SELinux 标签                  蓝牙域可读
/sdcard/Download/...                    media_rw_data_file            ✗ FUSE 拒绝
/sdcard/Android/data/<pkg>/files/...    media_rw_data_file            ✗ FUSE 拒绝
/data/local/tmp/ugreen_bridge/...       shell_data_file               ✗ 跨域被拒
/data/misc/bluetooth/logs/...           bluetooth_logs_data_file      ✅ 唯一可行

[教训] 跨进程共享文件，光看权限位不够，必须看 SELinux 标签（ls -lZ）。
```

## 7.2 ClassLoader（出现三次）

```text
❌ ColorOsBatteryBridge.class.getClassLoader()
   → 模块自己的 ClassLoader，看不到目标进程的类
   → 真机表现：所有类报"类不存在"

✅ lpparam.classLoader（LSPosed 在 handleLoadPackage 给的）
```

## 7.3 类加载时机

```text
handleLoadPackage 在【进程创建最早期】执行，
那时 AdapterService 等类还没加载 → Class.forName 报"类不存在"

解决：双重触发 —— 进程加载装一次，
      再 Hook AdapterProperties 的【构造函数】等蓝牙服务就绪后装第二次。
      钩构造函数而不是某个回调方法，因为构造函数不会随版本改名。
```

## 7.4 Java 字段前向引用

```java
private static volatile int currentMode = MODE_NOISE;   // 第 70 行
private static final int MODE_NOISE = 5;                // 第 645 行 ← 在后面

→ 编译错误"非法前向引用"。常量必须先声明。
```

## 7.5 lambda 自引用

```kotlin
val gatt = UgreenT6Gatt(
    onServicesReady = { gatt.enableAllCustomNotifications() }  // ← 变量还在构造中
)
→ "Unresolved reference: gatt"
修复：改用字段 t6Gatt?（回调是异步的，那时字段已赋值）
```

## 7.6 混淆导致方法名不可用

```text
COUI 库被 R8 混淆：
    com.coui.appcompat.preference.COUIJumpPreference
    方法名：[A, A0, B, B0, ... z, z0]

→ 不能按方法名找 onBindViewHolder
→ 改为按【签名 + 字段类型】识别（见 5.2）
```

## 7.7 照搬别的项目 = 白干

```text
照着 HuaweiPods 的类名去 com.android.bluetooth 里找降噪接口：
    com.android.bluetooth.ble.app.headset.BinderC6776v
真机探测：5 个候选类【全部不存在】

[教训] 先探测再实现。这也是本项目坚持"先写探测钩子"的原因。
```

## 7.8 RecyclerView 复用覆盖监听

见 5.2 末尾。**监听必须每次绑定都重挂。**

## 7.9 Android 的 stopped 状态

```text
现象：每次重启后要手动打开一次模块 APP 才生效
原因：新安装/刚更新过的应用被系统标记为 stopped，
      stopped 应用收不到 BOOT_COMPLETED、后台组件不能拉起
处理：加 BootReceiver + 手动打开一次，之后就不用再管了
```

## 7.10 跨进程文件"写了没人读"

```text
MelodyProviderHook 最初把降噪切换写成 AncRequest 文件，
但【没有任何代码读它】→ 用户点降噪"没有反应"。

[教训] 每次引入跨进程通道，必须同时想清楚"谁来读"。
       后来统一改成广播。
```

# 9. 已知未完成 / 可优化项

```text
① 切换延迟 ~1.5 秒
   原因：T6BleSender 用短连接（连接→发现→写入→断开）
   优化方向：APP 在线时优先走 APP 的常连接（需改优先级 + 就绪广播）
   权衡：长连接会和另一进程抢耳机

② 首次安装需要手动打开一次模块 APP
   原因：Android 的 stopped 状态（见 7.9）
   可优化：安装后主动启动一次（超出模块能控制的范围）

③ 降噪档位只用了 3 个
   T6 实际有 5 档（关/深度/中度/轻度/环境音）
   系统只给 3 个位置（关/降噪/通透）
   中度、轻度未接入，可考虑"长按循环"或放到自己的 UI

④ 设备快连弹窗未实现（已论证不可行，见 5.3）

⑤ 电量显示未接入分耳/仓
   ColorOS 的基础电量通道只有单个整数；
   分耳/仓需要另找接口（AirPodsManager 里有 batteryLevel 分组常量）
```
