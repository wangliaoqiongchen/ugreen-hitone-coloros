# 单耳断链问题：根因分析与修复

> 日期：2026-10-03
> 状态：已定位并修复（待真机验证）

---

## 1. 问题现象

```text
T6 在"单耳"过渡时（取出一只耳机 / 放回一只耳机）
会主动断开 BLE 链路，导致我们的 APP 掉线。

实测时序（早期捕获）：
    +33.258  RX  85 86 87 04 08 64 64 4A     ← BYTE4 由 01 变 08
    +33.283  GATT 状态变化：status=19 (0x13)
    +33.284  T6 GATT 已断开                   ← 仅 25ms 后断链
```

---

## 2. 关键事实核查：这不是我们代码的 bug

**官方"声学"APP 也一样在断连重连。** 从 bt_stack 日志统计：

```text
bluetooth_20261003_135449.log：
    connectSocket 发起        30 次
    on_cli_rfc_connect 成功   23 次     ← 30 次尝试只有 23 次成功
    cleanup_rfc_slot 断开     29 次
    ACL 断开(LE)              17 次
    ACL 连接(LE)              17 次

时间线可见快速重连：
    16:02:39.173  发起连接
    16:02:39.184  发起连接
    16:02:39.184  发起连接      ← 同一时刻连发三次
```

```text
[结论] "单耳断链"是 T6 固件的固有行为，任何 APP 都无法阻止。
       区别只在于【断开之后能不能自动恢复】。
       官方 APP 靠反复重连兜住，我们的 APP 之前是彻底断掉。
```

---

## 3. 根因：两个叠加的错误

### 错误 1：`connectGatt` 用了 `autoConnect = false`

```kotlin
// 修改前（UgreenT6Gatt.kt 第 674-679 行）
device.connectGatt(
    context,
    false,                      // ← autoConnect = false
    gattCallback,
    BluetoothDevice.TRANSPORT_LE
)
```

```text
Android 文档定义：
    autoConnect – Whether to directly connect to the remote device (false)
                  or to automatically connect as soon as the remote device
                  becomes available (true).

autoConnect = false 的后果：
    · 只发起【一次】连接尝试
    · 一旦断开，系统不再重试
    · 必须由 APP 自己轮询重连，否则永远连不回来
→ 这正是"单耳切换后掉线且不恢复"的主要原因
```

### 错误 2：断开回调里调用了 `closeGatt()`

```kotlin
// 修改前
BluetoothProfile.STATE_DISCONNECTED -> {
    onConnectionStateChanged(false)
    onServicesReady(false)
    clearQueues()
    closeGatt()                 // ← 注销 GATT 客户端
}
```

```text
closeGatt() 会注销 GATT 客户端。
即使把 autoConnect 改成 true，只要断开时执行了 closeGatt()，
自动重连机制就【永远不会生效】。

→ 两个错误叠加，导致行为完全等同于"一次性连接"。
```

### 附带发现：`disconnect()` 也有 bug（autoConnect 场景下才暴露）

```kotlin
// 修改前
fun disconnect() {
    try { bluetoothGatt?.disconnect() } catch (...) {}
    // ← 没有 closeGatt()
}
```

```text
如果只 disconnect() 而不注销 GATT 客户端，
autoConnect = true 会【立刻把连接又拉回来】，
用户表现："点了断开却断不掉"。
（这个 bug 在 autoConnect = false 时看不出来，
  改成 true 之后才会暴露。）
```

## 4. 修复内容

### 修复 1：`autoConnect` 改为 `true`

```kotlin
bluetoothGatt =
    device.connectGatt(
        context,
        true,               // ← 改为 true，由系统负责自动重连
        gattCallback,
        BluetoothDevice.TRANSPORT_LE
    )
```

### 修复 2：断开回调不再 `closeGatt()`

```kotlin
BluetoothProfile.STATE_DISCONNECTED -> {
    log("T6 GATT 已断开（status=$status）")
    onConnectionStateChanged(false)
    onServicesReady(false)

    clearQueues()           // 只清队列，保留 GATT 客户端

    if (status != BluetoothGatt.GATT_SUCCESS) {
        log("警告：异常断开（status=$status），自动重连可能失效，请手动重连")
    } else {
        log("等待系统自动重连（autoConnect=true，耳机可用时会自动连回）")
    }
}
```

```text
保留 GATT 客户端 = 保留自动重连能力。
status 非 0 表示异常断开（而非正常掉线），
此时系统可能已注销客户端，所以给出明确的提示。
```

### 修复 3：`disconnect()` 补上 `closeGatt()`

```kotlin
fun disconnect() {
    try { bluetoothGatt?.disconnect() } catch (...) {}
    closeGatt()     // ← 注销客户端，确保 autoConnect 不会立刻连回来
}
```

## 5. 为什么选 autoConnect 而不是自己写重连循环

对比两种方案的优劣：

```text
【方案 A】autoConnect = true（已采用）
    ✅ 一行代码，系统负责重连调度
    ✅ 系统级实现，比 APP 自己轮询省电得多
    ✅ 不占用 APP 的生命周期（APP 被杀也能由系统维持重连）
    ✅ 这是华为那种系统级集成的自然做法
    ❌ 重连时机不可控（由系统决定）
    ❌ 异常断开（status != 0）时可能失效，需手动兜底

【方案 B】自己写重连循环
    ✅ 时机完全可控（可精确控制退避策略）
    ❌ 需要 APP 常驻前台/前台服务
    ❌ 耗电，且 APP 被杀就失效
    ❌ 可能与系统自身的连接调度互相打架

【结论】优先用系统能力（方案 A），只在异常断开时手动兜底。
```

## 6. 参考：官方 APP 的重连策略（反编译 bt_stack Hook 得到）

虽然我们最终用系统 autoConnect，但官方/华为实现里的思路值得记录：

```java
// 来自 HuaweiPods 的 com.android.bluetooth 作用域 Hook
// 1) 15 秒防抖：同一设备 15 秒内不重复探测
Long last = lastProbeTime.get(deviceAddr);
boolean allowed = (last == null)
        || elapsed < last
        || elapsed - last >= 15000;
if (!allowed) { return; }

// 2) 单飞：同一时刻只允许一个探测在跑
if (!inFlight.compareAndSet(null, device)) { return; }

// 3) 延迟 5.5 秒后再执行 DeviceInfo 探测
handler.postDelayed(probeRunnable, 5500L);
```

```text
要点：
  · 防抖窗口 15 秒 —— 避免短时间疯狂重试
  · 单飞标志     —— 避免并发重连互相干扰
  · 延迟 5.5 秒  —— 给耳机留出稳定时间

这三条思路与我们观察到的官方 APP 行为一致：
官方 SPP 日志里能看到"连发三次连接尝试"的重试风暴，
也需要这类防抖与单飞来收敛。
```

```text
[后续] 如果 autoConnect 的自动重连在实际使用中感觉迟钝，
       可以在这套系统机制之上，再加一层"
       检测到断开 + 等待 N 秒 + 主动重新 connectGatt"的兜底，
       并复用上面的"防抖 + 单飞"两条原则。
```

## 7. 验证方式

```text
1. 重新编译安装我们的测试 APP
2. 连接 T6 并订阅 Notify
3. 做这些动作，观察日志与连接状态：
     a. 取出一只耳机      → 预期：断链，日志出现"等待系统自动重连"
     b. 把那只耳机放回     → 预期：系统自动连回，日志出现"T6 GATT 连接成功"
     c. 两只都取出         → 预期：链路保持（早期实测两只同取不会断）
     d. 两只都放回仓       → 预期：断链后再次自动连回
4. 点界面【断开 T6】→ 预期：真正断开，且不会被自动连回
```

```text
判据：
  · 日志里能看到 "等待系统自动重连" 之后跟着 "T6 GATT 连接成功"
    → autoConnect 生效
  · 点断开后不会自己连回来
    → disconnect() 的 closeGatt() 生效
  · 若异常断开（status != 0）后连不回来
    → 属于系统 autoConnect 的局限，需要补手动兜底
```

```text
[RUNTIME_VERIFIED] autoConnect = true 生效：
                   三次断开全部自动连回，无需人工干预。
                   重连耗时 0.45s / 0.93s / 2.08s。
[RUNTIME_VERIFIED] 断开原因都是 status = 19 (0x13)，
                   即"远端主动断开"，来自耳机固件，非本地错误。
```

### 9.2 暴露出的新问题：重连后 Notify 断流

```text
断开前：#0097 ~ #0110   收到了 RX NOTIFY
重连后：#0112 ~ #0342   只有 Service Discovery，【零个 RX NOTIFY】
```

```text
[根因] GATT 断开再连回时，系统会清掉 CCCD 订阅状态。
       我们的代码在重连后没有重新写 CCCD，
       所以虽然链路连上了，但耳机不再推送数据。
[后果] 表现就是"重连成功了，但数据全没了"，
       单耳场景下等于状态完全失明。
```

### 9.3 修复：重连后自动恢复 Notify 订阅

```kotlin
// 新增状态位：记录"用户希望订阅"
private var notifyDesired = false

// enableAllCustomNotifications() 开头
notifyDesired = true

// onServicesDiscovered() 末尾（服务发现完成后）
if (notifyDesired) {
    log("检测到之前已订阅 Notify，重连后自动恢复订阅")
    enableAllCustomNotifications()
}
```

```text
[RUNTIME_VERIFIED] 校验：5 处改动位置正确，括号平衡，无重复定义。
[待验证] 重连后是否重新收到 RX NOTIFY。
```

### 9.4 已知遗留：断开按钮失效

```text
现象：连点两次【断开 T6】，没有断开。
```

```text
[影响评估] 不影响最终目标。因为最终形态是"常连"，
           UI 上不会出现"断开"这个动作。
[可能原因] 未确证。值得注意的一点：
           disconnect() 里 disconnect() + closeGatt() 之后，
           STATE_DISCONNECTED 回调仍会到达，而那时 bluetoothGatt 已是 null。
[处理] 暂不深挖，避免在非关键路径上消耗时间。
       若将来需要，再加一个"用户主动断开"标志位来区分回调来源。
```
